# 사용자 에러 문구 스킬

## 이 스킬을 쓰는 법 (Claude Code에게)

이 스킬을 쓰는 앱들은 **팀원 대부분이 비개발자**다. 화면에 뜬 한 줄이 그 사람이 가진 정보의
전부이고, 거기서 "내가 뭘 잘못했나 / 기다리면 되나 / 누구에게 말해야 하나"를 판단한다.
그래서 `duplicate key value violates unique constraint "sites_pkey"` 같은 문장은 정보가
아니라 **소음**이고, `오류가 발생했습니다` 는 소음도 아닌 **공백**이다.

따라서 에러 처리 코드를 건드릴 때는:

1. 아래 **빠른 체크리스트**를 코드에 대고 점검한다.
2. 문구를 고칠 땐 그냥 바꾸지 말고 **"사용자가 이 문구를 보고 무엇을 할 수 있나"** 를 한 줄로
   설명하고 고친 판을 제시한다. 할 게 없는 문구는 아직 안 고쳐진 것이다.
3. 사용자가 "문구"를 말하지 않아도, 에러 경로를 만지면 자동으로 적용한다.

문서 구조: **1~3번은 문구를 쓸 때**, **4번은 코드 구조를 세울 때**, **5~7번은 에러 경로를
설계할 때**, **8·9번은 재시도와 응답 계약을 정할 때** 본다. 맨 끝 사고 사례는 각 절이 왜 있는지에 대한 실제 증거다.

## 빠른 체크리스트 (에러 코드 작성·리뷰 때 항상)

**문구 (→ 1번, 2번)**
- [ ] `오류가 발생했습니다` 를 단독으로 쓰지 않았는가? (무엇이 실패했는지가 없다)
- [ ] 문장이 `~습니다` 로 끝나는가? 명사형 종결(`재분석 실패`, `순서 변경 실패`)이 아닌가?
- [ ] 요청은 `~해 주세요` 로 띄어 썼는가? (`해주세요` 붙임 금지)
- [ ] 사용자가 스스로 못 고치는 실패에 `담당자에게 문의해 주세요.` 를 붙였는가?
- [ ] 반대로, 사용자가 고칠 수 있는 입력 오류에 문의 안내를 **붙이지 않았는가**?
- [ ] 제약이 있는 실패인데 **제약을 안 알려주고** "다시 입력해 주세요" 로 끝내지 않았는가? (→ 1번)

**재시도·코드 (→ 8번, 9번)**
- [ ] 재시도해도 결과가 같은 실패(403·404·409·422)에 **"다시 시도" 버튼을 달지 않았는가**?
- [ ] 기계용 코드를 응답에는 담되 **화면에는 띄우지 않았는가**?

**노출 (→ 3번)**
- [ ] 예외 원문(`error.message`, `str(exc)`)이 화면으로 가는 경로가 없는가?
- [ ] 응답 본문·JSON 조각·URL 경로·HTTP 상태 숫자가 문구에 섞이지 않았는가?
- [ ] 환경변수명·테이블/컬럼명·제약조건명이 문구에 없는가?
- [ ] 영문 `detail` 이 그대로 사용자에게 도달할 수 있지 않은가?

**구조 (→ 4번, 6번)**
- [ ] 레포에 **헬퍼 하나**가 있고, 화면에 문구를 띄우는 모든 경로가 거기를 지나는가?
- [ ] `원문 ?? 한국어폴백` 이 아니라 **`검증된 서버 문구 ?? 상태별 사전`** 순서인가?
- [ ] 기술 정보를 지우지 않고 `console.error` / 서버 로그로 **옮겼는가**?

**상태 구분 (→ 5번)**
- [ ] `isError` 와 `length === 0` 이 **다른 문구**로 갈라져 있는가?
- [ ] 404(없음)와 5xx(조회 실패)를 같은 화면으로 뭉뚱그리지 않았는가?

## 1. 문구 골격

> **[무엇이] [어떻게 됐습니다]. [왜 그런지]. [사용자가 할 일]해 주세요.**

세 요소다 — **무엇이** 실패했는지, **왜**(제약·조건), **어떻게** 하면 되는지.
가운데를 빼먹기 쉬운데, 그게 빠지면 사용자는 같은 실수를 반복한다.

```
△  가격을 저장하지 못했습니다. 다시 입력해 주세요.
      → 뭘 어떻게 고쳐야 하는지가 없다. 사용자는 같은 값을 또 넣는다.
✓  가격은 0보다 큰 숫자여야 합니다. 다시 입력해 주세요.
      → 제약이 드러나 있다.
```

제약이 따로 없는 실패(서버 오류 등)는 두 요소만으로 충분하다.

```
✗  오류가 발생했습니다.
      → 무엇이? 내가 뭘 하면 되나? 아무것도 없다.
✗  저장 실패
      → 명사형 종결. 통보문이라 차갑고, 다음 행동이 없다.
✗  저장 실패: duplicate key value violates unique constraint "sites_pkey"
      → 원인은 정확한데 읽을 수 있는 사람이 팀에 몇 명 없다.
✓  같은 이름의 현장이 이미 있습니다. 다른 이름으로 저장해 주세요.
```

### 어미 규칙

| 항목 | 규칙 |
|---|---|
| 종결 | **`~습니다`** 합쇼체. 명사형 종결 금지 |
| 요청 | **`~해 주세요`** (띄어쓰기). 보조용언 띄어쓰기 원칙 |
| 문의 | **`담당자에게 문의해 주세요.`** — `관리자에게` 아님, 변형 금지 |
| 마침표 | 제목(title)은 **없이**, 설명(description)은 **찍는다** |

### 문의 안내를 붙이는 기준

문의 안내는 **사용자가 스스로 할 수 있는 게 없을 때만** 붙인다. 고칠 수 있는 사람에게
남에게 물어보라고 하면 오히려 막막해진다.

| 붙인다 | 붙이지 않는다 |
|---|---|
| 권한 부족 (403) | 입력값 오류 — `다시 입력해 주세요` |
| 계정 상태 이상 (비활성·승인 대기) | 파일 형식·용량 — `10MB 이하로 줄여 주세요` |
| 서버 오류 (5xx) | 빈 목록 — 애초에 에러가 아니다 |
| 설정 누락 (503) | 세션 만료 — `다시 로그인해 주세요` |
| 재시도해도 계속 실패 | 중복 (409) — `다른 이름으로 저장해 주세요` |

**검증법:** 문구를 소리 내어 읽고 "그래서 나는 지금 뭘 하면 되지?" 에 답이 나오는지 본다.
안 나오면 아직 안 고쳐진 것이다.

## 2. 상태 → 기본 문구 사전

서버가 사용자용 문구를 주지 못했을 때 쓰는 최종 폴백이다. 레포마다 이 표를 그대로 옮겨 담는다.

| 상황 | title | description |
|---|---|---|
| 네트워크 실패 | `서버에 연결하지 못했습니다` | `인터넷 연결을 확인한 뒤 다시 시도해 주세요.` |
| 400 · 422 | `입력한 내용을 확인해 주세요` | (검증된 서버 문구가 있으면 그것) |
| 401 | `로그인이 만료되었습니다` | `다시 로그인해 주세요.` |
| 403 | `이 작업을 수행할 권한이 없습니다` | `담당자에게 문의해 주세요.` |
| 404 | `요청하신 자료를 찾을 수 없습니다` | `주소가 바뀌었거나 삭제되었을 수 있습니다.` |
| 409 | `다른 곳에서 먼저 변경되었습니다` | `새로고침한 뒤 다시 시도해 주세요.` |
| 413 | `파일 용량이 너무 큽니다` | `{N}MB 이하로 줄여 다시 올려 주세요.` |
| 415 | `지원하지 않는 파일 형식입니다` | `{허용형식}만 올릴 수 있습니다.` |
| 429 | `요청이 많아 잠시 제한되었습니다` | `{N}초 후 다시 시도해 주세요.` |
| 5xx | `처리하지 못했습니다` | `잠시 후 다시 시도해 주세요. 계속되면 담당자에게 문의해 주세요.` |
| 알 수 없음 | `처리하지 못했습니다` | `잠시 후 다시 시도해 주세요. 계속되면 담당자에게 문의해 주세요.` |

동작을 아는 자리에서는 `처리하지` 를 그 동작으로 바꾼다 — `저장하지 못했습니다`,
`불러오지 못했습니다`, `삭제하지 못했습니다`. 사전은 어디까지나 **모를 때의 바닥**이다.

**검증법:** 각 상태를 실제로 일으켜 화면을 본다. status 만 보고 표를 옮겨 적었는지,
정말 그 문구가 뜨는지는 다른 문제다.

## 3. 화면에 내보내지 않는 것

아래는 **지우는 게 아니라 로그로 옮기는** 것들이다(→ 6번). 화면에서만 사라진다.

- Supabase/Postgres 원문, 제약조건명, 테이블·컬럼·스키마명
- 환경변수명 (`SESSION_SECRET 누락` 은 사용자에게 아무 뜻이 없다)
- 스택트레이스, `str(exc)`, `JSON.stringify(error)`
- 응답 본문 원문, URL 경로, HTTP 상태 숫자 단독
- 영문 `detail` — `"User profile not found"`, `"Unauthorized"`, `"invalid id"`

**유일한 예외는 렌더 오류의 `digest`** 다. 서버 로그와 대조할 유일한 끈이라 남기되,
`<details>` 로 접어 평소엔 보이지 않게 한다.

```tsx
{error.digest && (
  <details className="mt-2 text-xs text-muted-foreground">
    <summary className="cursor-pointer select-none">자세히</summary>
    <p className="mt-1 font-mono">오류 코드: {error.digest}</p>
  </details>
)}
```

**검증법:** 아래가 전부 0 이어야 한다.

```bash
grep -rn "toast\.error([^\"']*\.message" src --include=*.tsx
grep -rn "instanceof Error ? .*\.message" src --include=*.tsx
grep -rn 'detail=f"[^"]*{e' backend
```

## 4. 레포마다 헬퍼 하나 — 규칙은 문서가 아니라 코드로 강제한다

레포마다 **헬퍼 하나**를 세우고 화면에 문구를 띄우는 모든 경로를 그리로 경유시킨다.
같은 규칙을 호출부마다 복붙해두면 나중에 추가되는 경로에서 **반드시** 빠진다
(→ 2026-08 검색 사례와 정확히 같은 이유).

이름과 위치는 레포 관례를 따른다. 강제로 통일하지 않는다 — 통일해야 하는 건 **구조**다.

### 핵심: 우선순위를 뒤집는다

흔한 관용구 `e instanceof Error ? e.message : "한국어 폴백"` 은 **원문이 항상 이긴다.**
`e` 는 거의 언제나 Error 라서 폴백은 죽은 코드다. 순서를 뒤집어야 한다.

> **① 네트워크 오류 → 고정 문구
> ② 서버 문구가 "사용자용"으로 판정되면 → 그대로
> ③ 아니면 상태별 사전(→ 2번)
> ④ 호출부가 준 fallback
> ⑤ 최종 폴백**
>
> **어느 경로로 가든 원문은 `console.error` 로만 나간다.**

TypeScript 참조 구현:

```ts
export type UserMessage = { title: string; description?: string };

/* 백엔드가 준 문자열을 사용자에게 보여도 되는지 판정한다.
   백엔드를 전수 정리해도(→ 7번) 이 그물은 남긴다 — 새로 추가되는 라우터에서
   반드시 빠지기 때문이다. */
function isUserFacingKorean(s: string): boolean {
  if (!s || s.length > 200) return false;
  if (!/[가-힣]/.test(s)) return false;                     // 영문 detail 전량 차단
  if (/[{}[\]]|"\w+":/.test(s)) return false;               // JSON 조각
  if (/Traceback|SQLSTATE|psycopg|violates|constraint/i.test(s)) return false;
  if (/relation "|column "|null value/i.test(s)) return false;
  if (/^\d{3}\s|\/api\//.test(s)) return false;             // "404 /api/..." 형태
  return true;
}

export function toUserMessage(err: unknown, fallback?: UserMessage): UserMessage {
  if (isNetworkError(err)) {
    return { title: "서버에 연결하지 못했습니다",
             description: "인터넷 연결을 확인한 뒤 다시 시도해 주세요." };
  }
  const serverText = extractServerText(err);   // detail·error 를 둘 다 읽는다
  if (serverText && isUserFacingKorean(serverText)) {
    return { title: serverText };
  }
  return byStatus(statusOf(err)) ?? fallback ?? {
    title: "처리하지 못했습니다",
    description: "잠시 후 다시 시도해 주세요. 계속되면 담당자에게 문의해 주세요.",
  };
}

/** console.error(기술 정보) + toast.error(사용자 문구) 를 한 번에. */
export function toastError(err: unknown, scope: string, fallback?: UserMessage): void {
  console.error(`[${scope}]`, err);           // 원문은 여기서 끝난다
  const { title, description } = toUserMessage(err, fallback);
  toast.error(title, description ? { description } : undefined);
}
```

Python (FastAPI) 참조 구현 — 한국어 기본값을 가진 팩토리:

```python
def forbidden(message: str = "이 작업을 수행할 권한이 없습니다. 담당자에게 문의해 주세요.") -> HTTPException:
    return HTTPException(status_code=403, detail=message)


def not_found(message: str = "요청하신 자료를 찾을 수 없습니다.") -> HTTPException:
    return HTTPException(status_code=404, detail=message)


def upstream_failed(message: str = "처리하지 못했습니다. 잠시 후 다시 시도해 주세요.") -> HTTPException:
    """DB·외부 연동 실패. 원문은 호출부에서 로그로 남기고 여기엔 싣지 않는다."""
    return HTTPException(status_code=502, detail=message)
```

**검증법:** 헬퍼를 거치지 않고 화면에 문구를 띄우는 경로가 남았는지 grep 한다(→ 3번).
헬퍼만 만들고 호출부를 안 옮기면 아무것도 고쳐지지 않는다.

## 5. 조회 실패와 빈 목록은 다른 문구

쿼리가 500 으로 죽었는데 표에 `집계할 대상이 없습니다` 가 뜨면, 그건 0건이라는 뜻이라
**원인을 정반대로 가리킨다.** 실제로 이것 때문에 "데이터가 날아갔다"는 오해가 있었다
(→ 2026-06 사례).

- `isError` 와 `length === 0` 은 **다른 문구**로 갈라서 보여준다.
- 404(없는 자료)와 401·5xx(조회 실패)도 마찬가지다. 전부 `notFound()` 로 보내면
  백엔드가 500 을 내도 화면엔 `페이지를 찾을 수 없습니다` 가 뜬다.

```ts
if (e instanceof ApiError && e.status === 404) {
  notFound();          // 정말 없는 것
}
throw e;               // 나머지는 에러 바운더리로 — "없음" 으로 위장하지 않는다
```

상태 화면은 `StateView` 의 `empty | error | forbidden | loading` 4상태를 쓴다.
빈 상태는 회색 톤, 오류는 경고 톤 — **색만 봐도 갈라져야 한다.**

**검증법:** 백엔드를 내린 채 목록 화면에 들어가고, 다음으로 필터를 걸어 0건을 만든다.
두 화면의 문구가 같으면 회귀다.

---

## 6. 기술 정보는 지우지 말고 로그로 옮긴다

화면에서 뺀다고 없애면 장애 대응이 불가능해진다. **옮기는 것**이다.

프론트 — 모듈 접두 규약을 지킨다. 나중에 로그에서 골라내는 유일한 수단이다.

```ts
console.error("[fix-requests] 전송 실패:", error);   // error 객체 통째로 (스택 보존)
```

`.message` 만 찍으면 스택이 사라진다. 객체를 넘긴다.

백엔드 — 원문은 로그로, 응답에는 고정 문구만.

```python
except Exception as e:
    log_failure("site_reports.save", e, source_key=str(site_id))
    raise upstream_failed("저장하지 못했습니다. 잠시 후 다시 시도해 주세요.") from e
```

`from e` 로 원인 체인을 보존한다. 영속 로그 테이블이 있으면 거기에도 남긴다 —
단 **개인정보는 넣지 않는다.**

**검증법:** 에러를 한 번 일으킨 뒤, 화면에는 사용자 문구가 뜨고 **로그에는 원문이 남는지**
둘 다 확인한다. 하나라도 빠지면 절반만 한 것이다.

---

## 7. 백엔드 detail 계약

프론트 헬퍼가 서버 문구를 검증하긴 하지만(→ 4번), 그건 그물이지 계약이 아니다.
백엔드는 **`detail` 에 항상 사용자용 한국어 완성문**을 담는다.

- `detail=f"...: {exc}"` 금지. 원문은 로그로(→ 6번).
- 영문 detail 금지. `"User profile not found"` 가 아니라 `"사용자 정보를 찾을 수 없습니다"`.
- 내부 개발자 말투 금지. `"수정할 필드가 없음"`, `"INSERT 결과가 비어 있음"` 은
  사용자에게 도달할 수 있는 자리라면 완성문으로 바꾼다.
- 응답 필드명은 레포 안에서 **하나로** 고정한다. `detail` 과 `error` 가 섞이면
  클라이언트가 한쪽만 읽어 **서버가 보낸 한국어가 통째로 버려진다**(→ 2026-08 문구 사례).

status 는 뜻대로 쓴다 — 401(미인증) / 403(권한) / 404(없음) / 409(충돌) /
413(용량) / 415(형식) / 429(제한) / 502(DB·외부 연동 실패) / 503(설정 누락).

**검증법:** 전역 예외 핸들러가 쓰는 필드명과 클라이언트가 읽는 필드명이 같은지 직접 대조한다.
표면적으로는 아무 에러도 안 나기 때문에 grep 이 아니면 안 보인다.

## 8. 재시도를 제안할지 판단한다

`StateView` 의 `action` 자리에 **"다시 시도" 를 항상 달면 안 된다.** 눌러도 같은 결과가
나오는 실패에 재시도 버튼을 주는 것은 거짓 희망이다 — 사용자는 될 때까지 누른다.

| 상태 | 재시도 | 화면에 줄 것 |
|---|---|---|
| 네트워크 실패 · 408 | O | **다시 시도** |
| 429 | O (대기 후) | 남은 시간 안내. 버튼은 시간이 지난 뒤 활성 |
| 500 · 502 · 503 · 504 | O | **다시 시도** + 계속되면 담당자 문의 |
| 400 · 422 | X | 입력 화면으로 되돌리기. 무엇을 고쳐야 하는지(→ 1번) |
| 401 | X | **다시 로그인** |
| 403 | X | 담당자 문의 (재시도 버튼 없음) |
| 404 | X | 목록으로 돌아가기 |
| 409 | X | **새로고침** 후 다시 (재시도가 아니라 갱신이다) |

자동 재시도를 건다면 **지수 백오프**로 한다 — `min(base × 2^n + jitter, max)`, 3~5회까지.
jitter 가 없으면 여러 탭이 동시에 같은 순간 몰려 서버를 다시 밀어 넣는다.
단, 429 는 백오프를 계산하지 말고 **`Retry-After` 헤더를 그대로 따른다.**

TanStack Query 를 쓴다면 4xx 는 재시도하지 않게 막는다.

```ts
retry: (count, error) => {
  if (error instanceof ApiError && error.status < 500) return false;  // 눌러도 같다
  return count < 2;
}
```

**검증법:** 권한 없는 계정으로 관리자 화면에 들어가 본다. "다시 시도" 버튼이 보이면 틀렸다.

## 9. 기계용 코드와 사람용 문구를 분리한다

에러 코드(`ONBOARDING_REQUIRED`, `AUTH_TOKEN_EXPIRED` 같은 것)는 **클라이언트가 분기하려고**
있는 것이지 사용자가 읽으라고 있는 게 아니다. 둘을 한 응답에 같이 담되, **화면에 나가는 건
문구뿐이다.**

```json
{ "error": { "code": "ONBOARDING_REQUIRED",
             "message": "현장 정보를 먼저 등록해 주세요." } }
```

- `code` — 안정된 문자열. 클라이언트가 `switch` 로 분기한다. 화면에 절대 띄우지 않는다(→ 3번).
- `message` — 사용자용 완성문. 코드가 없거나 모르는 코드일 때도 이것만으로 말이 돼야 한다.

코드를 새로 만들 땐 `{도메인}_{카테고리}_{상세}` 처럼 계층을 갖는 이름을 쓴다. 다만
**이 규칙은 분기가 실제로 필요한 곳에만 적용한다** — 화면이 그냥 문구만 띄우고 마는 실패에
코드를 붙이는 건 유지비만 늘린다.

### 입력값 오류는 필드까지 알려준다

폼 검증 실패를 문장 하나로 뭉뚱그리면 사용자가 어느 칸을 고쳐야 할지 모른다.
서버는 필드별로 내려주고, 화면은 해당 입력칸 아래에 붙인다.

```json
{ "error": { "code": "VALIDATION_ERROR",
             "message": "입력한 내용을 확인해 주세요.",
             "fields": [ { "field": "email", "message": "이메일 형식이 올바르지 않습니다." } ] } }
```

`fields` 가 있으면 토스트 대신 **인라인**으로 보여준다 — 토스트는 사라지는데 폼은 남는다.

**검증법:** 폼에 일부러 두 칸을 틀리게 채워 제출한다. 두 칸 모두 표시되는지,
그리고 토스트가 아니라 칸 옆에 붙는지 본다.

## 사고 사례 아카이브

규칙 자체는 위 절에 있으니, 여기서는 무엇이 어떻게 터졌고 얼마나 나아졌는지만 남긴다.

### 2026-06 · assign 조회 실패가 "데이터 없음"으로 보였다 (→ 5번)

권한 정리 중 matview 조회가 500 으로 죽었는데, 화면에는 `집계할 대상이 없습니다` 가 떴다.
0건이라는 뜻이라 **"데이터가 날아갔다"는 오해**로 번졌다. 실제로는 한 행도 안 지워졌다.

원인은 `isError` 와 `length === 0` 을 같은 분기로 처리한 목록 컴포넌트였다.
같은 뿌리의 버그가 상세 페이지에도 있었다 — `try/catch` 가 모든 실패를 `notFound()` 로
보내서, 백엔드가 500 을 내도 `페이지를 찾을 수 없습니다` 가 떴다.

**교훈: 틀린 문구는 모르는 것보다 나쁘다.** 원인을 정반대로 가리키면 대응도 정반대로 간다.

### 2026-08 · 5개 앱 에러 문구 전수 정리 (→ 1번, 3번, 4번, 7번)

같은 킷과 같은 Supabase 를 쓰는 5개 앱(ax-portal · career · concrete · assign · Site-Info)의
에러 표시 경로를 한 번에 훑었더니, **그릇은 통일돼 있는데 문구만 레포마다 갈라져 있었다.**

일관됐던 것: `patterns/StateView` 4상태 컴포넌트, sonner 토스트, 한국어 존댓말,
`console.error("[모듈] ...")` 접두, 에러 바운더리에서 원문 대신 digest 만 노출.

갈라졌던 것:

| | `오류가 발생했습니다` | `~하지 못했습니다` | `해주세요` | `해 주세요` |
|---|---|---|---|---|
| ax-portal | 0 | 13 | 0 | 22 |
| Site-Info | 0 | 3 | 6 | 2 |
| assign | 1 | 4 | 6 | 20 |
| career | 1 | 11 | 5 | 13 |
| concrete | **30** | 15 | **36** | 15 |

원문 노출은 더 심했다. assign 은 `ApiError` 가 `` `${status} ${path}: ${body}` `` 를 message 로
쓰는 바람에 사용자가 `404 /api/engineers/a3f9: {"detail":"기술자를 찾을 수 없습니다."}` 를
봤다 — **안에는 멀쩡한 한국어가 있는데 JSON 껍데기째** 나갔다. ax-portal 은
`저장 실패: duplicate key value violates unique constraint "..."` 를,
Site-Info 는 `DB 오류: {e}` 를, career 는 `재분석 실패: {exc}` 를 그대로 내보냈다.
`e instanceof Error ? e.message : "한국어 폴백"` 관용구가 5개 레포에 퍼져 있었는데,
`e` 는 언제나 Error 라 **폴백은 한 번도 실행된 적이 없었다.**

필드명 불일치로 **서버가 보낸 한국어가 통째로 버려지는 버그도 2건** 나왔다.
career 는 Next route 가 `{error}` 로 주는데 클라가 `detail` 만 읽어
`"전체 업로드 용량이 200MB를 초과했습니다"` 가 사라졌고, Site-Info 는 전역 핸들러가
`{error}` 인데 `handleMutation` 이 `detail` 만 읽어 미처리 500 에 `요청 실패` 만 떴다.

처방: 레포마다 **헬퍼 하나**를 세우고 화면 경로를 전부 경유시켰다. 핵심은 우선순위를
`원문 우선` 에서 **`검증된 서버 문구 → 상태별 사전`** 으로 뒤집은 것이다(→ 4번).

**교훈: 폴백은 있다고 동작하는 게 아니다.** 다섯 레포가 전부 한국어 폴백을 갖고 있었지만
순서가 뒤라 단 한 번도 쓰이지 않았고, 아무도 몰랐다.

## 참고

8·9번 절은 [revfactory/harness-100](https://github.com/revfactory/harness-100) 의
`api-error-design` 스킬(Apache-2.0)을 참고해 보강했다. 가져온 것은 **재시도 가능 여부 판정표**,
**지수 백오프·Retry-After 구분**, **기계용 코드와 사람용 문구의 분리**, **필드별 검증 에러 구조**,
그리고 1번 절의 **"왜"(제약) 요소**다.

가져오지 않은 것도 적어 둔다 — 그쪽은 `AUTH_*`·`VALIDATION_*` 전 도메인 에러 코드 카탈로그를
제안하는데, 사내 5개 앱 규모에서는 유지비만 늘어 분기가 실제로 필요한 곳에만 코드를 둔다(→ 9번).
또 그쪽 예시 문구는 `재시도하세요`·`관리자에게 문의하세요` 체인데, 우리 표준은
`다시 시도해 주세요`·`담당자에게 문의해 주세요` 다(→ 1번).
